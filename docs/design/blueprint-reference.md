# Blueprint design reference

This is the reference for the "Blueprint" design system in `apps/platform`: a
cyanotype-blue palette, IBM Plex typography, condensed uppercase for
structure, and monospace for machine-generated values. It documents what
exists after the foundation work (tokens, Tailwind wiring, fonts, the linter,
theme switching, the app shell, and one shared page header). Nine of the ten
pages in the app still have their pre-redesign bodies — tables, cards,
buttons, badges on the old scale. That is expected. This document is written
for whoever migrates those page bodies next.

**`resources/css/tokens.css` is the source of truth for every colour in this
system.** Nothing in markup ever references a raw Tailwind palette class
(`slate-400`, `indigo-600`, etc.) — every colour decision resolves through a
semantic token name. If you need a colour that doesn't exist yet, add a token
to `tokens.css`, not a one-off hex value in a component.

**If you change a value in `tokens.css`, run `npm run test:design` before
committing.** The contrast test (`tests/design/contrast.test.js`) recomputes
every pair below from the file itself and fails the build if any pair drops
below its WCAG minimum. There is no separate step to "remember" — the test
is the check.

## Type scale — seven steps, no exceptions

| Step | Size / line-height | Use |
|---|---|---|
| `text-2xs` | 10px / 14px | Structural labels and table heads. The only place condensed uppercase appears besides page titles. |
| `text-xs` | 11.5px / 16px | Monospace values, metadata |
| `text-sm` | 13px / 19px | Default body inside tables |
| `text-base` | 14px / 21px | Prose |
| `text-lg` | 16px / 22px | Section headings |
| `text-xl` | 20px / 25px | Modal and detail-page titles |
| `text-3xl` | 30px / 32px | Page titles, condensed uppercase |

There is no eighth step and no arbitrary size. `text-[Npx]` of any kind is
banned — `npm run design:lint` fails the build on any match, on migrated
paths. If a size you need doesn't fit one of these seven, that's a signal
the design needs a decision, not a one-off pixel value.

## Radius — three steps, nothing else

| Class | Size | Use |
|---|---|---|
| `rounded-sm` | 2px | Buttons, badges, form fields, the table shell |
| `rounded-md` | 3px | Cards, modals |
| `rounded-full` | — | Avatars and status dots only |

`rounded-none` is also allowed (its absence is the point, not an exception
to the scale). Every other radius step Tailwind ships — `lg`, `xl`, `2xl`,
`3xl`, and any arbitrary `rounded-[…]` value — fails `design:lint`. Most of
the old `rounded-full` badge pills read as near-rectangular now; that's the
direction, not a bug to fix.

## Condensed uppercase

IBM Plex Sans Condensed, uppercase, wide letter-spacing — reserved for two
things only:

1. Page titles (`text-3xl`, e.g. "APPLICATIONS", "CREDENTIALS VAULT").
2. Structural labels: table column heads, the sidebar's "WORKSPACE" and
   "TOOLS" labels, eyebrows above a title (`text-2xs`).

Nowhere else. Body copy, button labels, badge text, and table cell values
stay in regular IBM Plex Sans. If you find yourself reaching for condensed
uppercase to make something feel "more designed," that's the wrong instinct
— it's a structural marker, not a decorative one.

## Monospace is a UI face

Every machine-generated value — slugs, IDs, build hashes, ISO timestamps,
scopes (`credentials:write`), API key permission chips, byte counts — is set
in IBM Plex Mono, always. Human-authored text — names, descriptions, button
labels, prose — is always IBM Plex Sans. This is a binary rule with no
judgment call in the middle: if a value came from a human typing a name, it's
sans; if it came from a system generating or hashing something, it's mono.
Roughly seventy percent of the values on these screens are the latter.

## The expiry runway

The signature element for anything with a lifetime (certificates,
provisioning profiles, tokens, keys): a horizontal bar on **one shared time
scale across the whole application**.

- **Denominator is a fixed 365-day window, clamped.** Every runway bar in the
  app divides by the same 365 days, regardless of what's visible on the
  current page. A one-year credential fills about 62% of the bar; something
  valid for 25 years clamps to full with a `+` marker; an expired credential
  fills in `danger`. Never compute the denominator from the current page's
  data (e.g., "longest visible expiry") — that would make bars incomparable
  between pages and change the scale every time the underlying data changes.
- **`no expiry` renders as a dashed hairline, not an empty bar.** An empty
  bar reads as "expired"; a dashed line reads as "there is no scale here."
  Never render a zero-width or missing bar for a credential with no
  expiration.
- Tone (the bar's fill colour — `brand`, `warn-fill`, or `danger`) is derived
  from the remaining days, never passed in by the caller. A caller-supplied
  tone could disagree with what the bar actually shows.
- The bar is a meaningful graphic (WCAG 1.4.11, 3:1), not decoration — pair
  it with a text label stating the exact value, both for sighted users
  glancing at a page of bars and for screen readers.

The vault (`Pages/Credentials/Index.svelte`) has a hand-rolled version of
this bar today with its own local 90-day window — that is the pre-redesign
implementation and does not yet reflect the 365-day rule above. The shared
`Runway` primitive that replaces it is out of scope for this plan; building
it against the rule above (not against the vault's current 90-day behavior)
is part of the next sub-project.

## What's already true everywhere (all ten pages)

These are wired into the app shell and the fonts, so every page gets them
for free without migrating:

- IBM Plex Sans / Sans Condensed / Mono are self-hosted and loaded (no CDN
  dependency — the product must work in a closed network).
- Theme switching (light/dark) with no flash on load, driven by
  `resources/js/design/theme.js` and a boot script in `app.blade.php`.
- A visible cyanotype focus ring (`:focus-visible`, 2px, 2px offset) on every
  interactive element.
- `prefers-reduced-motion: reduce` neutralises transitions.
- One page header (`Components/ui/PageHeader.svelte`, used via the rewritten
  `Components/WorkspacePage.svelte`) instead of the old two-skeleton split.
  It supports an eyebrow, a condensed-uppercase title, a description,
  breadcrumbs, and an actions row.

## What's still on the old system (nine pages)

Everything below `PageHeader`/`WorkspacePage` on most pages — tables, cards,
buttons, filter chips, badges, modals — is still the pre-redesign markup:
`rounded-xl`/`rounded-2xl` corners, indigo buttons, raw `slate-*` text and
backgrounds. That is the expected, correct state this plan leaves things in.
`app.css` still carries the old `@layer base` element selectors (`button`,
`input`, etc.) and `@layer components` classes (`.card`, `.secondary`,
`.chip`, …) specifically so those unmigrated pages don't render unstyled.
Those layers get deleted only as their last consumer is migrated — do not
delete them early, and do not be surprised to see both systems coexisting on
the same page (a migrated header sitting above an unmigrated card is
correct, not a bug).

A few pages hand-roll their own header directly against dark-background-only
assumptions (hardcoded `text-slate-950` titles, for instance) because they
bypass `WorkspacePage` entirely (`ApiKeys/Index`, `Team/Index`,
`Billing/Index`, `Profile/Edit`, `Apps/AppLayout`) or use `WorkspacePage`'s
`heading` escape hatch (`Tools/PushNotifications`). In dark theme their
titles are low-contrast or unreadable. This is known, it is not something to
patch in isolation, and it goes away once each page's header is rebuilt on
`PageHeader` during migration.

## Before committing

Run:

```
npm run verify
```

from `apps/platform`. It chains three checks in order:

1. `npm run test:design` — the contrast test, token-name parity between
   light and dark, and the design-linter's own unit tests.
2. `npm run design:lint` — greps the migrated paths (currently
   `resources/js/Components/ui`, `resources/js/design`,
   `Components/AppShell.svelte`, `Components/WorkspacePage.svelte`) for
   arbitrary type sizes, raw palette classes, and off-scale radii. This list
   grows as more pages migrate — widen the path arguments in `package.json`
   as you convert a page, not the rules themselves.
3. `vite build` — a production build, to catch anything the first two don't
   (missing imports, Svelte compile errors, etc.).

All three must pass before a commit that touches design tokens, Tailwind
config, or anything under `resources/js/Components/ui`.
